# 维护与同步

[返回总目录](README.md) · [变更记录](CHANGELOG.md)

这是一套与项目同目录维护的 Markdown 规范。总入口为 `DESIGN.md`；本目录总目录可逐项进入细节。

## 文档分层

| 文档 | 内容 | 更新方式 |
| --- | --- | --- |
| foundations/ | Token 语义、字体、间距、主题等基础规则 | 人工维护 |
| components/ | 已有组件的样式、用途、状态和行为 | 人工维护 |
| patterns/ | 表单、错误、账单等组合规则 | 人工维护 |
| reference/ 中的常用名词 | 尚未建立的通用组件规范 | 实现后人工补充与移动 |
| tokens/ | 每个变量独立页面、声明条件和设计说明 | 生成区自动，其他区域人工 |
| reference/token-catalog.md | 所有实际导入的项目 CSS 变量链接 | 生成区自动 |
| reference/source-map.md | 样式导入路径和实现定位 | 生成区自动 |
| reference/source-snapshot.json | UI 源码哈希，供漂移检查 | 同步命令生成 |

## 修改代码后的步骤

1. 定位改动涉及的基础、组件、页面模式与 Token 文档。
2. 更新人工章节中的样式、规则、状态、示例、例外与实现状态；写出变更原因。
3. 若新增或移除名词，同步总目录及所有相关链接。
4. 修改 CHANGELOG；已存在条目只改受影响内容，不为一次改动复制整套规范。
5. 执行 `npm run docs:sync` 刷新 Token 声明、导入来源与源码快照。
6. 执行 `npm run docs:check`，再做与改动匹配的构建/业务测试和浏览器检查。

## 你直接修改文档时

- 可以直接修改每一篇 Markdown 的人工部分，记录新的颜色、间距、组件规则或使用方式。
- 尚未同步到代码的内容标注“待实现”，保留原实现与目标规则的区别。
- 后续明确要求实现时，再将代码与文档一起修改；不会仅因你编辑文档就擅自改变页面。
- 生成区使用 `<!-- generated:start -->` 和 `<!-- generated:end -->` 标记；其中的代码快照会被同步覆盖，个人要求写在标记外。
- 文件移名后同步目录和反向链接，不保留悬空链接。

## 检查命令的边界

`docs:check` 检查链接是否存在、Token 是否有独立页面、源码及既有规则来源是否相对快照改变、主题文档是否过长。它不会理解规则含义，也不证明人工文档与页面语义一致。

`docs:sync` 只提取实际入口导入的项目 CSS 声明，不计算完整浏览器级联，不把最后一条声明当作无条件最终值。Tailwind 内置变量和未导入的历史主题不进入 Token 清单。

这不是后台自动监控服务。持续维护依靠本项目 `AGENTS.md` 的任务约定；未来在此目录执行 UI 修改时，须同步文档。你在其他工具里直接改源码后，运行检查可以发现漂移，但使用规则仍需人工或后续任务更新。

## 每个组件页面必须包含

只填写现有文件中明确的规则并附来源。样式、用途、变体、状态、示例没有确定依据时，保留章节标题，内容留空。代码记录不能自动升级为已确定规范；不以模板完整为由推定设计意图。

## 维护记录格式

日期 / 对象 / 修改前后 / 原因 / 关联页面 / 实际验证 / 待完成项。未完成的验证明确标注，不沿用历史截图的结论。

## 规则确认约束（2026-11-24）

用户要求“只写已确定的，不确定的先空着”。以 [规则来源与取舍](reference/rule-sources.md) 为入口；已有文件注明候选、建议、未冻结的内容不填入已确定规则。后续明确修订优先于早期局部要求；范围不同的文档保留其范围，不推定全局替换。
